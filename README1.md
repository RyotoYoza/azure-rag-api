# Enterprise RAG API on Azure

A document-grounded question-answering API, deployed to Azure Container Apps through a fully automated pipeline. Every change — application code, infrastructure, or prompt — goes from `git push` to production through automated tests, a reviewable infrastructure diff, and a model-quality regression gate.

**The application is deliberately small. The platform around it is the point.**

Three properties are worth stating up front, because they are what this project set out to demonstrate:

- **No credentials exist anywhere.** Not in the repository, not in the container image, not in the running application, not in GitHub Secrets. The app authenticates to Azure OpenAI, PostgreSQL and the container registry with a managed identity; the deployment pipeline authenticates to Azure with OIDC federated credentials.
- **Infrastructure is reviewable before it happens.** Every pull request posts a `terraform plan` as a comment. A resource being destroyed shows up in code review, not in an incident.
- **Model quality is a merge gate.** A regression suite runs against the deployed system on every merge. Prompt and model changes are treated as code changes, because they can break the product without breaking a single unit test.

## What it does

`POST /ask` takes a question and returns an answer grounded in a corpus of internal IT support documents, along with the source files the answer was drawn from.

```bash
curl -X POST "$APP_URL/ask" \
  -H "Content-Type: application/json" \
  -d '{"question": "Why does the VPN keep dropping?"}'
```

```json
{
  "answer": "Check the JP-Cert-2026 machine certificate — it expires annually on 31 March and is re-issued by Intune only if the device checks in during the two-week window before expiry. An expired certificate produces error AEG-4412 in the client log.",
  "sources": ["vpn_connectionDrops.md"]
}
```

`GET /health` returns a liveness signal used by the platform's health probe and by the deployment pipeline's smoke test.

**How a question is answered.** The question is converted to a 1536-dimension embedding, PostgreSQL returns the *k* nearest document chunks by cosine distance (`pgvector`'s `<=>` operator), those chunks are inserted into the system prompt, and the model is instructed to answer using only that context. If the corpus does not contain an answer, the model says so — asking it the capital of France returns "I don't know", which is the clearest available demonstration that answers come from the documents rather than from the model's own knowledge.

The knowledge base is a set of fictional internal IT support documents (`docs/kb/`) with invented error codes, certificate names and version numbers. They are fictional deliberately: a corpus the model could answer from memory would prove nothing.

## Architecture

<!-- Keep the two Mermaid diagrams here. Caption each one — a reader who

*Request path — every arrow into a secret-bearing resource is authenticated by managed identity. No credential exists in the repository, the image, or the running container.*

*Deployment path — a merge to `main` is the only human action. Everything after it is automated, and the eval gate is the last thing standing between a merge and a live regression.*

### Components

| Resource | Purpose | Notes |
| --- | --- | --- |
| Container Apps | Runs the API | Scale-to-zero; costs nothing while idle |
| PostgreSQL Flexible Server | Vector store | `pgvector` extension, `vector(1536)` column |
| Key Vault | Holds the database connection string | Password generated by Terraform, never seen by a human |
| Container Registry | Holds the application image | Images tagged with the commit SHA |
| Log Analytics + Application Insights | Telemetry | Per-request tokens, cost, and latency |
| User-assigned managed identity | The app's identity | Scoped to exactly three resources |
| Azure OpenAI | Chat and embedding models | Lives in a separate resource group, outside Terraform's lifecycle |

## Quick start

### Run locally

```bash
git clone <repo-url> && cd azure-rag-api
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# Local vector store
docker run -d --name rag-postgres \
  -e POSTGRES_PASSWORD=localdev -e POSTGRES_DB=ragdb \
  -p 5432:5432 pgvector/pgvector:pg16

cp .env.example .env    # then fill in your Azure OpenAI endpoint and key
python -m app.ingest    # loads docs/kb/ into the vector store
uvicorn app.main:app --reload
```

Open <http://127.0.0.1:8000/docs>.

### Deploy to Azure

```bash
cd infra
terraform init
terraform apply -var-file=dev.tfvars
```

Then push an image and re-apply, or simply merge to `main` and let the pipeline do it. The pipeline path is the supported one; the manual path exists for bootstrapping.

### Configuration

All configuration is read from the environment — the same code runs locally, in a container, and in CI, with different values and different credentials behind it.

| Variable | Purpose |
| --- | --- |
| `AZURE_OPENAI_ENDPOINT` | Azure OpenAI resource endpoint |
| `AZURE_OPENAI_API_KEY` | Local development only; unset in Azure |
| `AZURE_OPENAI_API_VERSION` | API version string |
| `AZURE_OPENAI_CHAT_DEPLOYMENT` | Chat model deployment name |
| `AZURE_OPENAI_EMBED_DEPLOYMENT` | Embedding model deployment name |
| `DATABASE_URL` | PostgreSQL connection string; injected from Key Vault in Azure |
| `USE_MANAGED_IDENTITY` | `true` in Azure — authenticates without an API key |
| `APPLICATIONINSIGHTS_CONNECTION_STRING` | Telemetry; omitting it disables the exporter |
| `PRICE_INPUT_PER_1M` / `PRICE_OUTPUT_PER_1M` | Token pricing used for cost logging |

Model deployment names are never hardcoded. Azure retires models on a rolling schedule (a deprecated model blocked the first deployment of this project), so a forced model migration is a one-line change to a `tfvars` file that must pass the eval gate before it can merge.

## Prerequisites

### Azure resource providers

A fresh subscription does not have all resource providers enabled, and the resulting errors are misleading — an unregistered `Microsoft.Storage` reports as `SubscriptionNotFound`. Register these once per subscription:

```bash
for ns in Microsoft.Storage Microsoft.ContainerRegistry Microsoft.App \
          Microsoft.OperationalInsights Microsoft.DBforPostgreSQL \
          Microsoft.KeyVault Microsoft.ManagedIdentity Microsoft.Insights; do
  az provider register --namespace $ns
done

az provider list --query "[?registrationState=='Registered'].namespace" -o table
```

### Bootstrap resources (created manually, by design)

Three things are created by hand and deliberately live outside Terraform's control, because **a system cannot manage the thing it depends on to run**:

| Resource | Why it is outside Terraform |
| --- | --- |
| State storage account (`rg-tfstate`) | Terraform cannot store its state in a resource it has not created yet |
| Azure OpenAI (`rg-shared`) | Carries model deployments and quota; `terraform destroy` must never remove model access |
| GitHub Actions app registration | The identity that runs Terraform cannot be destroyed by Terraform |

The pipeline's service principal also needs `Cognitive Services OpenAI User` on the Azure OpenAI resource — a data-plane role that `Contributor` does not confer.

## Pipeline

### On every pull request

| Check | Purpose |
| --- | --- |
| `ruff check` / `ruff format --check` | Style, enforced not applied — CI verifies, it never rewrites your commits |
| `pytest` | Unit tests, with the LLM and database mocked |
| `docker build` | Proves the image still builds; does not push |
| `terraform fmt` / `validate` / `plan` | Plan posted as a PR comment |

All four are required status checks. A failing check blocks the merge.

### On merge to `main`

1. Authenticate to Azure via OIDC — no stored secret
2. Run tests
3. Build the image and push it tagged with the commit SHA
4. `terraform apply`
5. Open the database firewall for the runner's IP, ingest the knowledge base, close it again
6. Smoke test `/health`
7. Run the eval gate

Every deployed image traces back to exactly one commit. Rolling back is deploying a previous SHA.

## Evaluation

`evals/dataset.json` holds 17 cases. `evals/run_evals.py` runs them against the **deployed** URL — not against a mock — and scores two things separately:

- **Retrieval accuracy** — did the expected source document come back?
- **Answer accuracy** — does the answer contain the facts it should, and does the system refuse questions outside its corpus?

Separating them turns "quality dropped" into a diagnosis: retrieval falling while answers hold points at chunking or embeddings; answers falling while retrieval holds points at the prompt or the model.

Three cases are **refusal** cases — questions the system should decline, because they are outside the knowledge base. A RAG system that answers them has stopped being grounded, and every grounded test case would still pass.

```bash
EVAL_BASE_URL=$(cd infra && terraform output -raw app_url) python evals/run_evals.py
```

The threshold is 85%, not 100%. Model outputs vary; a gate demanding perfection fails on noise and gets disabled within a week. The bar is set where a real regression trips it and normal variance does not.

## Observability and cost

Every request emits a structured log line with token counts, estimated cost, and latency split between retrieval and generation. These arrive in Application Insights as queryable custom dimensions rather than as text.

```kusto
traces
| where message == "ask completed"
| extend cost = todouble(customDimensions.cost_usd),
         tokens = toint(customDimensions.total_tokens),
         reasoning = toint(customDimensions.reasoning_tokens),
         latency = todouble(customDimensions.total_ms)
| summarize requests = count(),
            avg_cost_usd = avg(cost),
            avg_tokens = avg(tokens),
            avg_reasoning_tokens = avg(reasoning),
            p95_latency_ms = percentile(latency, 95)
```

**Reasoning tokens are logged separately.** The chat model bills them as output tokens although they never appear in the answer, so a cost figure that ignores them understates reality. They are also a direct diagnostic: high reasoning tokens plus `finish_reason: "length"` is the signature of an answer truncated to nothing — a failure this project hit in development, which returned HTTP 200 with an empty string and passed every unit test.

## Runbook

### Roll back a bad deployment

Container Apps retains previous revisions. To shift traffic back without rebuilding:

```bash
RG=$(cd infra && terraform output -raw resource_group)
az containerapp revision list --name ca-ragapi-dev --resource-group $RG -o table
az containerapp revision activate --name ca-ragapi-dev --resource-group $RG --revision <previous-revision>
```

To roll back properly — so that state and reality agree — revert the commit and let the pipeline deploy the previous SHA. The revision command is the fast mitigation; the revert is the fix.

### Rebuild the environment from nothing

```bash
cd infra
terraform destroy -var-file=dev.tfvars
terraform apply -var-file=dev.tfvars
```

Then merge any commit to `main`, or dispatch the CD workflow, to build and deploy an image and repopulate the knowledge base.

### Common failures

| Symptom | Cause | Fix |
| --- | --- | --- |
| `exec format error` in container logs | Image built for arm64 on Apple Silicon | Build with `--platform linux/amd64`; CI builds natively on x86-64 |
| `MANIFEST_UNKNOWN` on apply | Image tag mismatch | Terraform variable precedence: `-var` beats `tfvars` beats `TF_VAR_*` |
| `resource already exists — needs to be imported` | An apply failed partway; the resource exists in Azure but not in state | Delete the orphan, or `terraform import` it if it holds data |
| `AADSTS700213` in the pipeline | OIDC subject claim mismatch | The error prints the subject GitHub sent — compare it against the registered federated credential |
| 403 reading Key Vault during a local apply | The `kv_admin` role assignment follows whoever runs Terraform | See [Known limitations](#known-limitations) |
| Connection timeout from a local ingest | Home IP changed | Update `my_ip` in `dev.tfvars` and re-apply |

## Design decisions

**Secrets are eliminated in two different ways, deliberately.** The Azure OpenAI credential is removed *in code* — `DefaultAzureCredential` requests a token, and the same code path works on a laptop via the Azure CLI session, in CI via OIDC, and in the container via managed identity. The database password is removed *by the platform* — Container Apps fetches it from Key Vault using the app's identity and injects it as an environment variable, so the application code is unchanged and unaware.

**Bootstrap resources live outside the system they bootstrap.** State storage, the Azure OpenAI resource, and the pipeline's identity are created manually. This is not an oversight; a `terraform destroy` that can delete the state file, the model deployments, or the credential the pipeline needs to run leaves no way back.

**Ingestion is idempotent by truncation.** The table is emptied and rebuilt on every run, so running it twice produces the same result. Duplicate chunks are actively harmful in RAG — the top-*k* fills with copies of one passage, so the model sees one fact repeated instead of *k* different facts.

**Chunking is character-based with overlap, and crudely so.** 800 characters with 150 of overlap, chosen for being simple and explainable. The overlap exists because a hard split can separate a question from its answer. Splitting on markdown headings, or token-aware splitting, would be better.

**The Dockerfile installs dependencies before copying application code.** Dependencies change rarely and code changes constantly, so this ordering keeps the expensive `pip install` layer cached and turns rebuilds from minutes into seconds.

**`terraform plan` output is posted to pull requests.** This is the single practice most worth carrying to another team. It makes infrastructure changes reviewable in the same way code is, and it means a resource being destroyed appears in a diff before it appears in an incident.

## Known limitations

Written out because they are deliberate trade-offs rather than oversights, and because the production-grade version of each is worth being explicit about.

**The database is publicly reachable behind an IP allowlist.** Adequate for a demo, wrong for a regulated client. The production shape is a private endpoint on a VNet with `public_network_access_enabled = false`, with the Container App on the same network. The allowlist also breaks whenever a home IP changes, which is a small daily reminder of why it is the wrong design.

**The eval gate runs after deployment, not before.** With a single environment it detects a regression rather than preventing one from reaching users. The correct shape is deploy to dev → evaluate → promote to prod, which is what the environment-parameterized deploy workflow was built for; a second environment was scoped out on cost and time grounds, and `prod.tfvars` plus the reusable workflow remain in the repository. The complementary answer is automatic rollback on a failed gate, using the revision mechanism described in the runbook.

**The Key Vault admin role assignment follows whoever runs Terraform.** It is scoped to `data.azurerm_client_config.current.object_id`, so it flips between the developer and the CI service principal on alternating applies. The fix is an explicit list of principals with `for_each`. It is a good illustration of a broader point: convenience constructs that resolve to "whoever is running this" quietly reintroduce the non-determinism infrastructure-as-code exists to remove.

**Ingestion re-embeds the entire corpus on every run.** Fine at 40 chunks; wrong at 40,000. The production version tracks per-document content hashes and re-embeds only what changed.

**Retrieval is naive top-*k* cosine similarity.** No re-ranking, no hybrid keyword search, no query rewriting. Each of those measurably improves retrieval quality on larger corpora, and the eval suite is the mechanism that would let them be adopted with evidence rather than by assumption.

**Prompt injection is not solved.** User input is kept in its own message role, which raises the bar slightly. It does not eliminate the problem, and claiming otherwise would be dishonest.

**The pipeline's service principal holds `Contributor` and `User Access Administrator` at subscription scope.** It can therefore grant itself further access. Acceptable for a personal subscription; in an organization it would be scoped per resource group, with separate identities per environment and approval gates on anything touching production.

**Telemetry initialization is not wrapped in a try/except**, so a failure in the Application Insights exporter could take down the application at startup. Telemetry should never be able to break the service it observes.
